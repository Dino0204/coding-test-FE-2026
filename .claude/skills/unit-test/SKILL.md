## 원칙

- **테스트 케이스는 명세에서 가져온다.** 구현 코드를 보고 기대값을 만들지 않는다. 구현이 틀리면 테스트도 같이 틀리기 때문이다.
  - 1순위: `PROBLEM.md` 4절 표의 `예시` 열을 그대로 옮긴다.
  - 2순위: 규칙 문장에서 드러나는 경계값 (`null`, 두 글자 이름, 날짜가 넘어가는 시각 등).
  - 명세에 없는 동작(빈 문자열, 한 글자 이름 등)은 기대값을 **추측하지 않는다.** 면접관에게 물어볼 질문으로 정리해 사용자에게 전달한다.
- 대상은 `src/utils/`의 순수 함수다. 컴포넌트나 API 테스트는 사용자가 요청할 때만 쓴다.
- `src/mocks/`는 수정하지 않는다. 라이브러리도 추가하지 않는다.

## 작성 규칙

- 위치: 대상 파일 옆에 `<파일명>.test.ts`로 둔다 (`src/utils/format.ts` ↔ `format.test.ts`).
- `globals: true`이므로 `describe`/`it`/`expect`는 import하지 않는다.
- `describe`에는 함수 이름을, `it`에는 기대 동작을 한국어 문장으로 쓴다.
- `it` 하나에서는 규칙 하나만 검증한다. 입력과 출력만 바뀌는 케이스는 `it.each`로 묶는다.
- 시간대에 의존하는 함수(KST 변환)는 실행 환경의 TZ에 결과가 흔들리지 않는지 확인한다. 날짜가 넘어가는 케이스를 반드시 넣는다.

```ts
import { maskPatientName } from './format';

describe('maskPatientName', () => {
  it.each([
    ['홍길동', '홍*동'],
    ['김민', '김*'],
  ])('%s → %s', (input, expected) => {
    expect(maskPatientName(input)).toBe(expected);
  });
});
```

## 흐름

1. 대상 함수와 `PROBLEM.md`의 해당 규칙을 읽는다.
2. 케이스 목록(입력 → 기대값, 출처)을 사용자에게 먼저 보여 준다. 명세에 없는 케이스는 질문으로 표시한다.
3. 테스트 파일을 작성한다.
4. `npm test`를 실행해 결과를 그대로 보고한다.
   - 실패하면 테스트를 구현에 맞추지 않는다. 명세 기준으로 테스트와 구현 중 무엇이 틀렸는지 판단해 사용자에게 알린다.
5. 한 번이라도 실패를 봤다면 알린다. 구현을 잠깐 깨뜨려 테스트가 실패하는 것도 확인했다면 함께 알린다. 어느 쪽이든 AI_LOG `검증` 칸에 적을 근거가 된다.
6. 커밋은 `git-commit` 스킬로 `test(format): ... 테스트 추가` 형식을 따른다.
